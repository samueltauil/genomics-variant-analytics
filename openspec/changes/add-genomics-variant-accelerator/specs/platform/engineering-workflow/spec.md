## Purpose

Makes the repository the verifiable source of record for everything that produces a variant — pipeline definitions, infrastructure, notebooks, and reference manifests — so that a `pipeline_version` on a variant row resolves to signed, immutable, reviewable content rather than a free-text string.

## ADDED Requirements

### Requirement: Repository as source of record

The workflow definitions, infrastructure templates, analysis notebooks, reference-data manifests, and the accelerator's own specs SHALL be held in a single Git repository. Any artifact that a pipeline run depends on SHALL be resolvable to a commit SHA in that repository.

#### Scenario: Resolving a run to source

- **WHEN** a consumer resolves the workflow used by a pipeline run
- **THEN** a commit SHA in the repository is returned
- **AND** checking out that SHA yields the workflow definition, its container definition, and its reference manifest

#### Scenario: Untracked dependency

- **WHEN** a pipeline run declares a dependency that has no commit SHA in the repository
- **THEN** the run is rejected before compute is allocated

### Requirement: Pipeline version resolves to an immutable release

`pipeline_version` SHALL be the tag of an immutable release. Once published, the release tag SHALL be locked to its commit and its assets SHALL be locked against modification or deletion, and the release SHALL carry a release attestation recording the tag, commit SHA, and assets.

#### Scenario: Variant row resolves to a locked release

- **WHEN** a consumer takes `pipeline_version` from a variant record and looks it up
- **THEN** an immutable release is returned whose tag maps to exactly one commit SHA
- **AND** the release attestation is retrievable

#### Scenario: Attempt to move a published tag

- **WHEN** a push attempts to move or delete the tag of a published immutable release
- **THEN** the operation is rejected

#### Scenario: Tag reuse after deletion

- **WHEN** an immutable release is deleted and a new release attempts to reuse the same tag name
- **THEN** the tag name is refused

### Requirement: Build provenance for pipeline containers

Every container image used by secondary analysis SHALL carry a build provenance attestation generated by the build workflow, recording the source repository, commit, and workflow that produced it. The attestation SHALL be verifiable offline and SHALL be pushed to the registry that distributes the image, including when that registry is Azure Container Registry.

#### Scenario: Verifying an image before a run

- **WHEN** the pipeline submission path verifies the provenance attestation of the image it is about to run
- **THEN** verification succeeds and reports the originating repository, commit, and workflow

#### Scenario: Unattested image

- **WHEN** an image without a valid provenance attestation is submitted for a run
- **THEN** the run is rejected

#### Scenario: Registry carries the attestation

- **WHEN** the image is pulled from the container registry that distributes it
- **THEN** its provenance attestation is retrievable from that same registry

### Requirement: Toolchain bill of materials

Each pipeline container SHALL have a signed SBOM attestation enumerating the bioinformatics toolchain it contains, including aligner, variant caller, and utility versions. The SBOM for the container that produced a given variant SHALL be retrievable from that variant's `pipeline_version`.

#### Scenario: Establishing which tool called a variant

- **WHEN** an investigator asks which variant-caller version produced a specific variant record
- **THEN** the SBOM attestation reached through `pipeline_version` names the caller and its version

#### Scenario: Toolchain change is visible

- **WHEN** a container is rebuilt with an upgraded aligner
- **THEN** the new SBOM attestation differs from the prior one in that component's version

### Requirement: Genomic data excluded from version control

The repository SHALL prevent files carrying genomic or patient data from entering version control. Enforcement SHALL include a server-side gate that a contributor cannot satisfy by local configuration alone, and the repository SHALL declare which enforcement point applies to its visibility and account tier.

> Assumption: push rulesets — the strongest form of this control, applying at push time across the whole fork network — target private and internal repositories. A public repository must gate at merge instead, which leaves direct pushes to unprotected branches uncovered; the default branch is therefore protected and all changes arrive by pull request.

#### Scenario: Pull request adds a variant file

- **WHEN** a pull request contains a `.vcf`, `.bam`, `.cram`, or `.fastq` file
- **THEN** the data-hygiene check fails
- **AND** the pull request cannot be merged

#### Scenario: Pull request adds an oversized file

- **WHEN** a pull request contains a file exceeding the configured size limit
- **THEN** the data-hygiene check fails and the pull request cannot be merged

#### Scenario: Direct push to the default branch

- **WHEN** a contributor attempts to push directly to the default branch
- **THEN** the push is refused and the change is directed through a pull request

#### Scenario: Credential in a commit

- **WHEN** a commit containing a recognized credential pattern is pushed
- **THEN** the push is blocked and the detection is reported

#### Scenario: Enforcement point is declared

- **WHEN** a reader consults the repository's documentation
- **THEN** it states whether enforcement occurs at push time or merge time, and what that leaves uncovered

### Requirement: Secretless deployment

Deployment workflows SHALL authenticate to Azure using short-lived federated credentials issued per run. No Azure client secret, storage key, or connection string SHALL be stored as a repository or environment secret.

#### Scenario: Deployment authenticates

- **WHEN** a deployment workflow provisions or updates Azure resources
- **THEN** it obtains a short-lived token through federated identity
- **AND** the repository's configured secrets contain no Azure credential

#### Scenario: Credential added as a secret

- **WHEN** an audit enumerates repository and environment secrets
- **THEN** no entry is an Azure client secret, storage key, or connection string

### Requirement: Deployment approval and recording

Deployments to the clinical and research targets SHALL pass through named environments with required reviewers, self-approval disabled, and administrator bypass disabled. Each deployment SHALL produce a deployment record identifying the environment, the approver, the commit, and the outcome.

#### Scenario: Deployment awaits approval

- **WHEN** a workflow job targets the clinical environment
- **THEN** the job pauses until a required reviewer approves
- **AND** the environment's secrets remain inaccessible to the job until approval

#### Scenario: Self-approval attempt

- **WHEN** the user who triggered the deployment attempts to approve it
- **THEN** the approval is refused

#### Scenario: Deployment record

- **WHEN** an approved deployment completes
- **THEN** a deployment record is retrievable identifying environment, approver, commit, and outcome

### Requirement: Only released commits reach protected environments

Protected environments SHALL accept deployments only from tags of immutable releases, so that no unreleased commit can reach a clinical or research target.

#### Scenario: Deploying from a branch

- **WHEN** a deployment to the clinical environment is attempted from a feature branch
- **THEN** the deployment is refused

#### Scenario: Deploying from a release tag

- **WHEN** a deployment to the clinical environment is attempted from an immutable release tag
- **THEN** the deployment proceeds to the approval step

### Requirement: Repository-resident AI context

The repository SHALL carry the accelerator's domain rules as version-controlled Copilot context — instructions, reusable prompt files, and agent skills covering the VCF schema, the no-PHI constraint, reference-build handling, and the positioning constraints. This context SHALL be reviewed through the same pull-request path as code.

#### Scenario: Domain rule reaches the assistant

- **WHEN** a contributor asks Copilot to add a column to the variant store
- **THEN** the response reflects the repository's VCF schema rules and the no-PHI constraint without the contributor restating them

#### Scenario: Rule change is reviewed

- **WHEN** a domain rule in the AI context is changed
- **THEN** the change goes through pull-request review before taking effect

#### Scenario: Analyst reuses a prompt

- **WHEN** a research scientist runs a stored prompt file for cohort exploration
- **THEN** it executes against the current specs and schema without hand-written setup

### Requirement: Governed assistant access to variant data

Where an AI assistant is given access to variant data, it SHALL reach that data through a governed query interface that enforces the caller's access tier server-side. The assistant SHALL NOT be granted direct table or file access that bypasses those checks.

#### Scenario: De-identified caller asks a genomic question

- **WHEN** a caller holding de-identified access asks the assistant a cohort question
- **THEN** the answer is composed from governed query results with subject linkage withheld

#### Scenario: Assistant attempts direct access

- **WHEN** the assistant's configured tooling is inspected
- **THEN** it exposes only the governed query interface, not raw table or storage credentials

#### Scenario: Assistant activity is audited

- **WHEN** the assistant issues a query on a caller's behalf
- **THEN** the audit trail records the calling principal, the query, and the timestamp

### Requirement: Automated review of provenance-affecting changes

Pull requests that change workflow definitions, container definitions, reference manifests, or the variant schema SHALL receive an automated review before human review, checking reference-build compatibility, schema drift against the specs, and whether a version bump is required.

#### Scenario: Reference build changed without a version bump

- **WHEN** a pull request changes the declared reference build but not the workflow version
- **THEN** the automated review flags the missing version bump

#### Scenario: Schema drift

- **WHEN** a pull request adds a variant-store column that is absent from the specs
- **THEN** the automated review flags the drift and names the spec that would need updating

### Requirement: Scheduled pipeline triage

Failed pipeline runs SHALL be triaged on a schedule by an automated agent that opens a tracked issue per failure, carrying the failing stage, the run provenance, and the log location.

#### Scenario: Overnight failure

- **WHEN** a pipeline run fails outside working hours
- **THEN** the next scheduled triage opens an issue naming the failing stage, the run identifier, the reference build, the pipeline version, and the log location

#### Scenario: Repeated failure

- **WHEN** the same failure recurs for a run already triaged
- **THEN** the existing issue is updated rather than duplicated

### Requirement: Account-tier and size constraints are stated

Accelerator documentation SHALL state which platform controls in this capability depend on the repository's account tier or visibility, and SHALL name the substitute control where a tier-gated feature is unavailable.

> Assumption: the demo repository is public and lives in a personal account. Push rulesets require a private or internal repository, so the data-exclusion control gates at merge instead of at push. Assistant content-exclusion and centrally managed policy are organization-tier features and have no substitute here beyond the merge gate and the repository never holding data in the first place.

#### Scenario: Tier-gated feature is unavailable

- **WHEN** a control in this capability is unavailable on the deployment's account tier
- **THEN** the documentation names the substitute control and the resulting gap

#### Scenario: Reference data exceeds release asset limits

- **WHEN** a reference genome is too large to attach as a release asset
- **THEN** the release carries the reference manifest and checksums, and the data itself stays in object storage
- **AND** the manifest resolves to the object-storage location
